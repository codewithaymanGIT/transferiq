# TransferIQ

Premier League player market-value intelligence platform, per the full architecture
in `docs/phase-0-blueprint.md`. This README tracks what's actually built and verified
working, not just planned.

**Status: the full stack is real and running end-to-end -- data pipeline, database,
backend, frontend, and a trained ML model actively serving live predictions with
real per-player SHAP explanations.** The model is honestly weak (see "The ML model"
below) but every layer above it, from raw data ingestion to the rendered UI, is
genuinely wired together and working, not a mockup.

**Anti-fabrication contract, enforced by the schema, the API, and the model pipeline:**
`market_values` (external benchmark) and `predictions` (this project's own model
output) are separate tables, never conflated. `GET /players/{id}/valuation` returns
**404**, not a placeholder number, until a real `Prediction` row exists for that
player. Every prediction that *does* exist carries an honest `confidence` label
("Low" for the current model) and real, model-derived bounds -- never a fabricated
+/- percentage.

## Quick start

```bash
pip install -r requirements.txt
cp .env.example .env
docker compose up --build          # postgres + backend + frontend
# API docs:  http://localhost:8000/docs
# Frontend:  http://localhost:3001
```

If you're starting from a fresh clone/unzip and Postgres already has data loaded
from a prior run (a named Docker volume persists independently of the source
folder), you can skip straight to `python scripts/train/generate_predictions.py`
to regenerate live predictions against a running stack.

## Data sources (all verified against live pulls)

- **FPL official API** -- current player prices/form, official, no auth needed.
- **FBref** (via the `soccerdata` package) -- deep stats (minutes, goals, assists, xG
  where available) plus age, birth year, and nationality (captured as of this
  session -- previously discarded despite FBref already returning them). FBref sits
  behind Cloudflare bot protection; `soccerdata` handles this with real browser
  automation (`seleniumbase`), which on some Windows machines needs a Defender/
  antivirus exclusion for its driver folder. See `docs/data-sources/fbref.md`.
  **Currently loaded: 8 seasons (2016-17 through 2022-23, plus 2024-25).**
- **Transfermarkt** (via `ewenme/transfers`, a maintained CSV mirror) -- real historical
  transfer fees, 1992/93 through 2022/23. 23,675 records pulled, 1,657 matched and
  loaded against players in the database. See `docs/data-sources/transfermarkt.md`.

```bash
python scripts/ingest/run_ingest.py --provider fpl --season 2024-2025
python scripts/ingest/run_ingest.py --provider fbref --season 2024-2025
python scripts/ingest/run_ingest.py --provider transfermarkt   # full history in one pull, no --season
```

Each run writes `data/raw/<provider>/<season>_<utc-timestamp>.parquet` and never
overwrites a prior snapshot.

## Loading into Postgres

```bash
python scripts/load/load_to_postgres.py --season 2024-2025
python scripts/load/load_transfers.py
```

Reads the latest FBref snapshot, runs it through clean + validate, then upserts
players/clubs/season-stats (including date of birth and nationality, backfilled
without overwriting a previously-set real value). Idempotent -- re-running updates
existing rows instead of duplicating them. Multi-position players (e.g. FBref's
"FW,MF") take the first listed position as primary. Rows with an unparseable
position or missing identity are skipped and counted, never silently lost.

## The ML model

**Honest summary: a real, cross-validated, weakly-positive signal -- not a mature
model.** The full story, including two ruled-out hypotheses and the methodology
fix that changed the conclusion, is in `docs/model-comparison.md` (regenerated by
the command below, never hand-edited). Short version:

```bash
python scripts/train/build_training_matrix.py     # assembles data/processed/training_matrix.parquet
python scripts/train/train_baseline_models.py      # median -> Linear -> Ridge -> RF -> XGBoost, writes docs/model-comparison.md
```

- **128 real training rows** (transfer fee + leakage-safe prior-season stats),
  up from an initial 70 after loading more historical FBref seasons.
- **A single 80/20 train/test split proved too unstable to trust** at this sample
  size -- adding or removing one feature swung R2 by more than a full point on
  the same data. `train_baseline_models.py` now reports 5-fold cross-validated
  results as the primary metric, with the old single-split table kept for
  comparison.
- **`age_at_transfer`** (computed from a real birth year, never imputed for a
  player missing one) is by far the strongest feature -- confirmed independently
  by both Random Forest's Gini importances and real SHAP values, matching
  well-documented findings in football transfer economics.
- **Random Forest is the only model that beats a naive median-fee guess** under
  cross-validation (mean R2 = 0.063, std = 0.267 across folds) -- a real but
  fragile positive signal, not a production-grade model. Every other model
  (Linear, Ridge, XGBoost) underperforms the baseline.
- `transfer_year` was tested as a feature and dropped -- it made every model
  worse, not better, likely overfitting rather than capturing a real market-era
  effect at this sample size.

## Live predictions

```bash
python scripts/train/generate_predictions.py
```

Fits the final Random Forest on all 128 training rows, then scores every current
player with complete 2024-25 stats and a known birth year (players missing either
are skipped and counted, never imputed). Writes real `model_versions` and
`predictions` rows:

- **Prediction intervals** come from the Random Forest's own per-tree predictions
  (10th/90th percentile spread), not a fabricated +/- percentage.
- **`confidence` is honestly reported as "Low"**, matching the model's actual
  cross-validated quality -- stored in the database, not just mentioned in docs.
- **Real per-player SHAP contributions** (`shap_contributions`, JSONB) are computed
  and stored per prediction, converted from SHAP's native log-fee space to an
  approximate GBP-millions contribution via a documented first-order
  approximation -- surfaced live via `GET /players/{id}/valuation` and rendered
  as a "Why this valuation" breakdown on the player profile page.

As of the last run: 573/574 current players scored (1 skipped for a missing birth
year).

## Migrations

Alembic is set up (`alembic/`) with a deliberate no-op baseline -- the schema is
still authored by hand in `database/schema.sql` (loaded automatically by Postgres
on first container start) and mirrored in `backend/app/models.py`. See
`alembic/README` for the real workflow and a known gap it surfaced: three
optional/non-core tables (`player_comparisons`, `watchlist_players`,
`player_comparison_players`) exist in the schema but have no ORM class yet --
flagged rather than silently dropped or guessed at.

## Frontend

Dark charcoal-navy base, muted gold accent reserved for £ figures, `Space Grotesk`
headings / `IBM Plex Sans` body / `IBM Plex Mono` for all numeric data. Player
profile pages show a real valuation with its honest confidence label and a
per-feature "Why this valuation" SHAP breakdown when a prediction exists, or "no
model valuation yet" -- never a placeholder number -- when it doesn't.

```bash
cd frontend && npm install && npm run dev   # http://localhost:3000
```

## Testing

```bash
pytest tests/ -v      # 78 tests, all offline
```

Covers: provider shape contracts (static fixture and real-format samples),
cleaning/validation/transform logic (synthetic data), the FastAPI backend
(in-memory SQLite, including the "no fabricated valuation" 404 path), the
Postgres loader (in-memory SQLite, including idempotency and DOB/nationality
backfill), the training matrix's leakage guard, the model comparison script
(cross-validation, feature importances, SHAP, negative-result detection), and
the live-prediction script's core logic (age computation, honest skip-when-
missing-DOB behavior).
